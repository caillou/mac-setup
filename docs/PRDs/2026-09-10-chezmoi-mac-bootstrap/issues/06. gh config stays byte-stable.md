# gh config stays byte-stable

## PRD

[2026-09-10-chezmoi-mac-bootstrap](../prd.md)

Captured values, commands and sources are in [research-notes.md](../research-notes.md).

## What to build

Ship `~/.config/gh/config.yml` in the form gh leaves it, so an apply is never interrupted by an overwrite prompt.

- The defect, reproduced in the final right-thing review with gh 2.97.0 in an isolated `GH_CONFIG_DIR`: the first gh command to read the managed file appends `version: "1"` to it (a config-schema migration, not a login side effect; comments are preserved, 317 to 330 bytes). `.chezmoiscripts/run_after_30-github-and-ssh.sh.tmpl:59` runs `gh auth token` on every apply, so the first apply triggers it. From then on `chezmoi apply` and `chezmoi update` stop at `.config/gh/config.yml has changed since chezmoi last wrote it?` (with stdin closed, chezmoi v2.72.1 exits 1: `could not open a new TTY`), and `chezmoi status` shows `MM`. Answering "overwrite" reverts the file and gh re-adds the line on its next run, so the prompt comes back every time. Stories 2 and 45 and issue 05's "a second `chezmoi apply` is a no-op" all fail on it.
- Fix: append `version: "1"` (quoted, exactly as gh writes it) as the last line of `dot_config/gh/config.yml`. Verified byte-stable in the review: with the line present, `gh auth status`, `gh alias list` and `gh config get` leave the file byte-identical. Keep the comment header; gh preserves comments.
- The alternative the review named (stop managing the file and have script 30 run `gh alias set --clobber co 'pr checkout'`) is not taken: the file stays the source of truth for the alias and the script stays free of config writes.
- Test, next to the existing `gh reads the co alias out of the managed config` (`tests/git-github-ssh.bats:113-125`): copy the applied file aside, run the real `gh alias list` against `GH_CONFIG_DIR="$HOME/.config/gh"` in the isolated home, then `cmp` the copy against the file. Keep the `command -v gh || skip` guard so CI images without gh still pass.
