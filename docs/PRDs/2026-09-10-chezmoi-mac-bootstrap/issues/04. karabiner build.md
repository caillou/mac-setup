## What to build

Generate the Karabiner rules from the karabiner.ts source kept inside the dotfiles repo.

- Copy the source from the karabiner.ts repo into `.karabiner/` in the dotfiles repo (dot-prefixed, so chezmoi ignores it without a rule): the single TypeScript rules file, `package.json`, the lockfile, a minimal tsconfig, and a `.gitignore` with `node_modules/`. Drop the starter README; a few lines in the dotfiles README replace it.
- `run_onchange_after_50-karabiner.sh.tmpl`, hashed on the source and lockfile, guarded on Karabiner being installed: the facts include puts `~/.asdf/shims` on PATH (scripts don't inherit the shell config), then `npm ci` and the build, which writes the rules into Karabiner's config file, preserving its other settings.
- The source already targets "Default profile" (retargeted 2026-09-11), which Karabiner creates on first launch, so no profile has to be created by hand. Karabiner must have been launched once; the manual checklist covers that.
- Per the Karabiner research in the notes: keep karabiner.ts (maintained, 1.38.0, covers KE 16); pin it as `^1.38.0` with a committed lockfile; keep `tsx` as the runtime; add a `dev` script `tsx watch src/index.ts` for iterating; keep the `update` script for deliberate bumps. Alternatives (goku, kanata, KE's own JS evaluator) were evaluated and rejected.
- The generated `karabiner.json` never enters the repo.

## Acceptance criteria

- [ ] the build from the `.karabiner/` copy produces rules identical to the current ones (verified on this Mac in the migration issue)
- [ ] on a machine without Karabiner the script skips with a message
- [ ] changing the rules file and running `chezmoi apply` rebuilds; an unchanged source does not
- [ ] dependencies are pinned and `npm ci` is reproducible
